# PICO 4 + трекер глаз Paper

Исследовательский и инженерный проект для подключения стороннего **Paper Tracker** к стандартной версии **PICO 4 (A8110)**. Ближайшая цель — автономный bridge, который захватывает и обрабатывает изображения глаз непосредственно на шлеме. Совместимость с нативными играми, использующими отслеживание взгляда, и системный рендеринг с фовеацией по взгляду (ETFR) относятся к последующим этапам проверки и пока не являются готовыми функциями.

## Состояние проекта

Отдельный Java Activity для калибровки находится в [`paper-pico-bridge/calibration-app/`](paper-pico-bridge/calibration-app/). Он отображает девять целей по пути 2D virtual display PICO и запускает существующие root-инструменты захвата и создания artifact. APK теперь использует `su -mm -c` и не запускает PaperTracker. На проверенном A8110 Activity был назначен на частный virtual display 1602x902, но smoke test из shell оставил этот display в состоянии `OFF`, пока фокус сохранялся у PICO Shell; реальное отображение в шлеме, ввод и пользовательская калибровка ещё не подтверждены.

Поддерживаемая native-реализация находится в каталоге [`paper-pico-bridge/`](paper-pico-bridge/). Это отдельный native-проект на CMake, содержащий daemon для устройства, транспортные парсеры, декодирование JPEG, базовое определение зрачка, калибровку, версионированный ABI общей памяти, тесты и read-only probe для Zygisk Runtime.

Проверенная цепочка на самом шлеме:

```text
USB-устройства глаз Paper
→ настройка CDC и чтение bulk-IN
→ сборка raw JPEG
→ декодирование JPEG на Pico
→ поиск кандидата зрачка
→ временное сопоставление левого и правого глаза
→ публикация версионированного gaze sample
```

Сейчас предусмотрены ограниченные диагностический, записывающий, wake- и live-режимы:

- `--dual` — диагностический режим. Он захватывает оба глаза, декодирует кадры, запускает детектор зрачка и выводит статистику. Действительный gaze sample не публикуется.
- `--diagnose-eyes <seconds>` — ограниченная диагностика изображений: размеры, диапазон/среднее grayscale, доля тёмных пикселей, результаты базового детектора и первый JPEG каждого глаза в `/data/local/tmp/`. Это не меняет калибровочный путь.
- `--wake-stream <seconds>` выполняет статически восстановленную запись `WAKE,L=50,F=40\n` в bulk-OUT после настройки CDC и проверяет полные JPEG обоих глаз, не запуская PaperTracker.
- `--dual-live <seconds> <calibration-file>` — явный рабочий режим. Он требует корректный бинарный файл калибровки, сопоставляет наблюдения в окне 50 мс и публикует только свежие объединённые samples.
- `--target-record <id> <x> <y> <seconds> [csv]` добавляет помеченные наблюдения обоих глаз для одной отображаемой точки калибровки. Отдельный Pico Activity отображает цели и запускает команды захвата.

Каждая USB-команда ограничена диапазоном от 1 до 30 секунд и защищена эксклюзивным lock daemon. Конкурирующий запуск завершается ошибкой вместо конкуренции за USB Paper. При ошибке захвата любого глаза режим live не публикует завершающий heartbeat, а target recording откатывает строки этой точки. Режим live намеренно строгий: отсутствующий, обрезанный, CSV-, содержащий нечисловые значения или иным образом неправильный файл калибровки отклоняется; только в этом случае daemon записывает heartbeat о работоспособности, поэтому потребитель не может принять некалиброванный результат за пригодные координаты взгляда.

## Что проверено

### Оборудование Paper и USB-транспорт

Paper предоставляет три USB-устройства:

- Face: `0425:0001`
- Left eye: `0425:0002`
- Right eye: `0425:0003`

Bridge динамически определяет номер USB-шины, адрес устройства, CDC control interface, CDC data interface и bulk-IN endpoint. Он не зависит от фиксированного имени узла `/dev/bus/usb` или фиксированного endpoint. Наблюдавшаяся настройка CDC: 115200 baud, 8 бит данных, 1 stop bit, с установленным DTR.

На текущих устройствах глаз поток представляет собой непрерывные JPEG-данные, начинающиеся с `FF D8` и заканчивающиеся `FF D9`. В некоторых версиях APK Paper используются записи `JPG0`/`UVC0`; bridge сохраняет ограниченный incremental parser для этого формата и отдельный raw-JPEG parser. Оба варианта поддерживают границы USB-передач и повторную синхронизацию после повреждённых данных.

Daemon уже запускался на шлеме одновременно для обоих глаз. Он может захватить control и data interfaces, настроить serial-соединение, прочитать поток, декодировать JPEG, запустить детектор зрачка и освободить интерфейсы после окончания захвата. Для этой цепочки не требуется ПК или сетевой сервис, передающий координаты взгляда.

### Обработка изображения на устройстве

Текущий vision backend — небольшой переносимый базовый детектор:

1. Декодирует JPEG в изображение оттенков серого.
2. Оценивает яркость и выбирает адаптивный порог темноты.
3. Находит компоненты связности с четырёхсоседней связностью.
4. Отбрасывает кандидатов по площади, радиусу, соотношению сторон и confidence.
5. Возвращает наиболее сильный кандидат зрачка с координатами в пикселях и confidence.

Это рабочая базовая реализация для проверки интеграции, а не утверждение о равной точности с desktop-моделью Paper. Интерфейс изолирован, поэтому позднее его можно заменить более точной моделью без изменения USB- и shared-sample-контрактов.

### Калибровка и общие samples

Текущий estimator независимо подбирает двумерное projective homography-преобразование для каждого глаза. Он переводит координаты зрачка в нормализованную плоскость взгляда `[0,1]`, отклоняет нечисловые значения и почти нулевой projective denominator, а при калибровке проверяет ожидаемое направление слева направо и сверху вниз. Это перенос подтверждённых идей PC-процесса (`homography`, стабильные samples, center reference и direction checks), но не совместимый по бинарному или параметрическому формату порт проприетарной Windows-реализации.

Корректный сохранённый файл калибровки имеет ровно 216 байт и содержит:

```text
9 входных точек левого глаза
9 входных точек правого глаза
9 целевых точек
```

Все координаты должны быть конечными `float`, а оба преобразования должны быть численно корректными. CSV, создаваемый командой `--dual-record`, содержит только наблюдения: в нём нет меток целевых точек, поэтому это не файл калибровки.

ABI `GazeSample` содержит magic, версию, размер структуры, sequence, монотонную временную метку, флаги валидности, векторы левого/правого/объединённого взгляда, confidence и состояние источника. Публикация выполняется с sequence lock. Читатель отклоняет повреждённые, записываемые, некалиброванные, нездоровые, устаревшие samples и samples с нечисловыми координатами.

Текущий prototype использует файл общей памяти:

```text
/data/local/tmp/paper-pico-bridge.sample
```

Это внутренний путь прототипа, а не публичный сетевой протокол.

## Архитектурные выводы

### Paper является источником изображений

Paper предоставляет изображения глаз. В исходном desktop-сценарии gaze вычисляется на ПК из этих изображений. Автономный bridge переносит захват, декодирование, базовую обработку, калибровку и публикацию samples на Pico.

### Передача JPEG в нативный алгоритм Tobii больше не является планом

Реверс-инжиниринг показал, что активный алгоритм Pico Tobii использует проприетарные данные и не принимает обычный Paper JPEG как совместимый источник изображений. Поэтому вариант «передавать JPEG Paper в нативный алгоритм Tobii» больше не считается рабочим направлением.

Практическая архитектура:

```text
Изображения Paper
→ локальная обработка и калибровка на Pico
→ версионированный GazeSample
→ проверенный compatibility layer на стороне потребителя OpenXR Runtime
```

### Где Runtime получает данные

В текущей прошивке найден C++-метод:

```text
pvr::TrackingClient::GetEyeTrackingData(long, int, pxr_eyepose*)
```

Для текущей библиотеки проверены форма символа, сигнатура сборки и соглашение о передаче аргументов AArch64. Компонент Zygisk пока выполняет только:

- распознавание целевого процесса;
- динамический поиск отображения библиотеки;
- проверку пролога известной сборки;
- read-only проверку свежести shared sample.

Активный inline hook отключён. Неизвестные сборки Runtime, неверные layout выходной структуры, недействительные или устаревшие samples обрабатываются по принципу fail-closed и сохраняют исходное поведение Pico.

## Команды

Daemon поддерживает следующие команды разработки:

```text
--enumerate
```

Динамически ищет устройства Paper и их интерфейсы. Не выполняет claim и reset.

```text
--self-test
```

Создаёт или обновляет тестовый shared sample. USB не читает.

```text
--capture <pid> <seconds>
```

Захватывает одно выбранное устройство Paper и выводит диагностику parser, JPEG и детектора зрачка.

```text
--dual <seconds>
```

Параллельно захватывает оба глаза в диагностическом режиме. Действительный gaze не публикует.

```text
--diagnose-eyes <seconds>
```

Захватывает оба глаза с daemon-native wake, выводит размеры декодированных изображений, диапазон и среднее grayscale, долю тёмных пикселей и результаты диагностических преобразований. Сохраняет по одному первому JPEG в `/data/local/tmp/`; эти преобразования не используются калибровкой.

```text
--wake-stream <seconds>
```

Выполняет ограниченный native wake, записывает подтверждённую форму `WAKE,L=50,F=40\n` в bulk-OUT и проверяет полные JPEG обоих глаз, не запуская PaperTracker.

```text
--dual-record <seconds> [csv]
```

Захватывает оба глаза и записывает наблюдения зрачка с временными метками:

```text
timestamp_ns,eye,frame,x,y,radius,confidence,valid
```

```text
--dual-live <seconds> <calibration-file>
```

Загружает строгую бинарную калибровку, сопоставляет свежие наблюдения левого и правого глаза и публикует только калиброванные объединённые samples. При ошибке загрузки калибровки команда завершается с кодом `4` и записывает только heartbeat о работоспособности.

Режим daemon по умолчанию является безопасным idle skeleton. Он не захватывает USB автоматически.

## Безопасность и восстановление

Проект сохраняет нативное поведение Pico, если предварительное условие не доказано:

- нет записи в системный раздел;
- системные библиотеки Pico не заменяются;
- не используются фиксированные PID и фиксированные ASLR-адреса;
- в режиме сервиса нет автоматического USB reset;
- в поставляемом модуле нет активного inline patch OpenXR;
- устаревшие, недействительные, некалиброванные или нечисловые samples не публикуются;
- изолированный dispatch shim вызывает оригинальную функцию при fallback;
- Runtime и пролог проверяются по известной сборке;
- буферы кадров и длительность захвата ограничены.

Изолированный эксперимент ARM64 trampoline содержит сохранение исходных байтов, проверку установленного patch, очистку instruction cache, mutex процесса, остановку и возобновление соседних потоков на время записи и путь восстановления. Это всё ещё development artifact. Универсальная relocation PC-relative инструкций, полная семантика `pxr_eyepose`, время жизни replacement, координация выгрузки и реальная стабильность Runtime не доказаны.

## Что ещё не готово

До состояния рабочего bridge для нативных игр необходимы:

1. Пользовательская девятиточечная калибровка на Pico с созданием настоящего бинарного файла.
2. Измерения точности, дрожания, задержки и пропусков на реальной калибровке.
3. Проверенное преобразование нормализованной плоскости Paper в ожидаемую Pico 3D-систему координат взгляда.
4. Полное описание `pxr_eyepose`: семантика полей, валидность, время и соглашения координат.
5. Replacement-реализация, сохраняющая все исходные поля и безопасно возвращающаяся к оригинальному методу.
6. Короткая обратимая проверка совместимости Runtime и длительный тест стабильности.
7. Подтверждение, что нативная игра действительно потребляет полученные данные.
8. Проверка ETFR после предыдущих этапов; ETFR сейчас не включён и не заявляется как работающий.

## Сборка и границы развёртывания

Bridge собирается с помощью CMake, Ninja и Android NDK для `arm64-v8a` и API 29. Перед запуском `paper-pico-bridge/tools/build.ps1` задайте `ANDROID_NDK_HOME`:

```powershell
$env:ANDROID_NDK_HOME = 'C:\path\to\android-ndk'
./paper-pico-bridge/tools/build.ps1
```

Исходное дерево не включает каталоги сборки, сгенерированные библиотеки, APK, device captures, записи калибровки и ZIP-пакеты. Стандартный Magisk skeleton содержит daemon и библиотеку read-only probe; это не законченный продукт для внедрения gaze.
